## Destination

Reaching the destination does **not** mean v0.1 is built. §39's "Definition of done" is a *build* completion test, not this map's destination.

## Notes

**Domain.** Unpocketed: an open-source, local-first Android app for recording, importing, transcribing and exporting spoken audio. Backendless — no account, no Unpocketed server. Users bring their own transcription provider and API key. Core domain entities are **Recording** (the original audio; §3.2 "original audio is sacred") and **Transcript** (many per Recording, each attributed to a provider+model; §10). Stack is Expo + React Native + TypeScript, expo-audio, expo-sqlite, expo-secure-store, Uniwind (Tailwind 4), Expo Router.

**Skills every session should consult.** `mattpocock-skills:grilling` and `mattpocock-skills:domain-modeling` by default. Research tickets additionally use `mattpocock-skills:research`.

It is a small, separable follow-up, not a loose end inside PR8.

**The abstraction held, with one qualification worth stating precisely.** No provider-specific API logic landed outside `providers/transcription/`, which is §3.3's actual test, and Deepgram needed no new field on `TranscriptionResult` and no special-casing of synchronous providers beyond the `if (!provider.resume)` branch that already existed. What it *did* expose was an incomplete **failure vocabulary**, and in two places:

- **`insufficient-credit` is a new error kind.** Deepgram answers `402` when the project has no credit, and neither `unauthorized` (the key is fine) nor `provider-failed` (the request is fine) can say so. Under bring-your-own-key the balance is the user's, so running out is an ordinary state. AssemblyAI has the same condition — it was simply never discovered, because no transcription had run. Generic, not provider-specific.
- **A synchronous Provider makes "nothing was charged" unprovable.** `interrupted-before-upload` promised the user "nothing was transcribed or charged". For Deepgram there is never a job reference, because the transcript comes back in the reply, so a lost reply may mean work that ran and was billed. That copy now admits what it cannot know, and a separate `interrupted-unresumable` covers the case properly. This closes the `TODO(PR7 review)` in `errors.ts` that anticipated it as theoretical.

**Two bugs found while wiring the second provider**, both latent and both invisible with one Provider: `resumeJobFor` **and** `resumeOutstandingJobs` each resolved one Provider and polled every job with it, so the first switch would have sent an AssemblyAI job reference to Deepgram's endpoint with Deepgram's key. A `TODO(PR8)` marked the first site; **nothing marked the second**. Both now resolve from `job.providerId` — a job belongs to the Provider that took it for its whole life.

**One narrow stuck state, recorded so it is not rediscovered as a new bug.** A job with no reference whose Provider cannot be resolved — its key removed from Settings while it was in flight — is now skipped by the startup sweep rather than failed, and `useRecordingTranscription` will not re-attach to it either, because that guard requires a reference. The Recording reads `Transcribing…` with a disabled control until the key comes back. It is **not a regression**: the previous code abandoned the whole sweep in the same situation, so strictly more jobs are recovered now. Left alone in PR8 because failing it would mean claiming work was lost that may have completed and been billed, which is the judgement the rest of this feature is built on.

**The gate is closed. PR8's exit condition was met on device on 2026-10-08**, with a 90-second two-speaker recording transcribed by **Deepgram `nova-3`** and then by **AssemblyAI `universal-2`**, both transcripts coexisting and each correctly attributed. The first transcription in the project's life ran on that date; before it, every network path was unexercised.

What the live run settled, beyond "it works":

- **Deepgram's `arch` is the right attribution field.** It returned `nova-3`, resolving the uncertainty recorded in the adapter — Deepgram's own documented example contradicts itself on this field, so it could only be settled by observation.
- **Both transcript-id branches are exercised.** AssemblyAI's transcript is `txn-job-9257447901134180b03de2bda7da71a3`, derived from its job reference so completion is repeatable; Deepgram's is `txn-20261008101142-e9n5pj`, the random id taken when no reference exists. Both jobs cleared cleanly, leaving no sidecars.
- **The recorder negotiated ~97.7 kbps** (1,103,459 bytes for 90.4 s), which confirms the ~96 kbps measured at PR3 rather than the preset's requested 128 kbps.
- **§22 pays off immediately, and in both directions.** Each provider got something the other got wrong on the same audio. AssemblyAI heard *"Yes, today it is very good"* where Deepgram heard *"Yesterday, it is very good"* — AssemblyAI is right, since it answers a question about the weather. But Deepgram transcribed *"Hello. Good morning. Hello. Good morning."* where AssemblyAI gave only one *"Hello. Good morning."*, and the recording has two speakers greeting each other — so **AssemblyAI appears to have dropped a speaker turn**, which is a content loss rather than a formatting difference. Ticket 04 called quality "explicitly unverified" and rested the decision on caps, lifecycle and price; this is the first evidence on quality, and it does not favour either one outright. Deepgram also punctuates in short sentences where AssemblyAI uses commas, which reads more naturally.
- **The diarization gap is now evidence rather than theory.** The test recording is a two-person call and both transcripts are a flat run of text with no way to tell who spoke. §10's `Transcript.text` is a single string, so speaker information is discarded even though both providers offer diarization and `supportsDiarization` is already true for both. An LLM reading either transcript cannot recover the boundaries — it would have to invent them, which is the failure the two-stage decision above explicitly rules out. **§10 needs revisiting before the enrichment PR**, and that is a schema change, so it is cheaper decided before more transcripts exist on disk.

**Diarization was added to PR8 on 2026-10-08 (Devon's call), overriding §6's "speaker identification" non-goal and this map's own decision from the same morning to keep it out.** The argument that moved it: speaker turns can only come from the recogniser, so a transcript produced without them cannot gain them later without paying for the audio a second time — every Transcript made between now and the enrichment PR would have been permanently flat. §10 gains an optional `segments` array alongside `text`, which stays the primary form because §3.4 promises plain-text export and a Provider may return no turns at all.

**It is a setting rather than always-on, because it costs money.** AssemblyAI bills diarization as an add-on — **+$0.02/hr** against universal-2's $0.15, so ~13% — which ticket 04's costing did not carry. Deepgram documents no separate charge. Default on, with the cost disclosed in the Settings row per §19.

**Verified on device the same day**, and the route there is worth recording because two runs failed first for reasons that were not bugs:

- The two Providers agree on nothing but the question. AssemblyAI takes `speaker_labels: true` and returns `"A"`/`"B"` with **millisecond** offsets; Deepgram needs `diarize=true` **and** `utterances=true` together — either alone silently yields no speaker data — and returns `0`/`1` with **float second** offsets. Adapters normalise both to a 0-based index assigned in **order of first appearance**, never arithmetic on the label, which would break on a Provider numbering from one.
- **Two failed runs were not failures.** A test recording of one person voicing both halves of a conversation — including one voice deliberately muffled — was correctly reported as **one speaker** by both Providers. Diarization separates by vocal characteristics, not by conversational turn-taking, so one person is one speaker whatever they do with their voice. Any future diarization test needs **two real vocal tracts**; a recording of a television interview produced two speakers from both Providers immediately.
- **A genuine defect that run exposed:** `toSegments` filed turns carrying no speaker label under speaker 0, making "the Provider returned no speaker data" indistinguishable from "the Provider identified one speaker" — which is exactly what Deepgram returns for `utterances` without `diarize`. It now reports absent, so segments-present means diarization actually ran.
- **Granularity differs sharply and the interface has to absorb it.** On the same 75-second clip Deepgram produced **14** turns, fragmenting mid-sentence, where AssemblyAI produced **6** natural conversational ones. Consecutive turns by one speaker are therefore grouped under a single heading rather than rendered one per turn.
- **§10's warning is now demonstrated, not asserted.** The same Recording transcribed by both Providers assigns the *host* speaker index 1 under Deepgram and index 0 under AssemblyAI. A speaker index is a label inside one Transcript and nothing more.
- **A single speaker renders as plain text**, deliberately: tagging every line "Speaker 1" is noise. The cost of that rule is that a working pipeline looks identical to a broken one, which is what made the first failed run confusing.

**A quality signal against AssemblyAI, then retracted.** It dropped leading content twice — one of two greetings in the first test, and the cold-open line of the television clip that Deepgram caught — which looked like a pattern. **It is not.** A later run of the *same* recording with the *same* model recovered the cold-open line in full, so this is run-to-run variance rather than a systematic defect, and the earlier reading was two samples mistaken for a trend. Recorded because the wrong version of this was briefly acted on: ticket 04's "quality is explicitly unverified" still stands, and nothing here moves it.

**Also fixed in passing:** the Home screen's AI Provider tile was hardcoded to "Not configured" from PR1's static interface, so the first screen in the app told a fully configured user they had set nothing up.

**Step 18 found a real defect, which is what it was written for.** Leaving the screen mid-transcription stranded the Recording on `Transcribing…` for the rest of the session with nothing polling it. AssemblyAI's `submit` took the caller's abort signal, but §18 defines that signal as *"stops polling; does not cancel the provider's job"* — and submitting is not polling, it is the step that **creates** the job. A Back press after the upload had finished (uploads ignore the signal and cannot be stopped) aborted the one request that would have turned those bytes into a transcript, leaving a job with no reference that nothing could re-attach to and an upload spent for nothing. Deepgram's adapter had already got this right; AssemblyAI's had not. Two secondary faults came with it: the screen's re-attach guard required a job reference, so a job stranded without one was never resolved within a session; and the spinner read the stored job's state while the button read a separate `busy` flag, so the screen offered "Try again" beside a spinner that never appeared for a minute at a time. One signal now, folded into §21's state.

**Still unexercised** (the device script's sections 4 and 5): every failure path — bad key, offline, and the two interrupted-mid-transcription cases — plus the hour-long recording, where Deepgram's 10-minute processing ceiling is expected to be a real risk rather than a bug.

**Superseded, kept for the record: no transcription had ever actually run.** No key has been configured for either Provider, so the entire network half — upload, submit, poll, and every failure path including the two error kinds added above — remains unexercised. PR8's exit condition cannot be *met* by code review. It needs an AssemblyAI key and a Deepgram key, and a device run of `.scratch/v0-1-derisk/pr8-device-test.md`. Free credit covers it many times over: AssemblyAI gives $50 at signup and Deepgram $200, against $0.15 for an hour of audio.

- **Transcription and enrichment are two provider layers, not one** (2026-10-08, Devon's call, taken at the start of PR8): a Recording is processed in two stages, and only the first is in v0.1. **Stage one is speech-to-text** — audio in, a Transcript out — and that is what `TranscriptionProvider` and §3.3's abstraction mean. AssemblyAI and Deepgram belong here, as would an on-device model later. **Stage two is enrichment** — a Transcript in, a derived structure out: the title, sub-headline, executive summary, overview, formatted speaker turns and conclusion that `docs/UnPocketed-Example-*.png` show on the transcript screen. An LLM answers that, and the candidates named were Claude, OpenAI and Gemini.

  **PR8 is stage one only.** The provider picker chooses a speech recogniser; it must never also offer the model that writes a summary, because those are two different knobs and §3.6 prefers one obvious control to one clever one. Enrichment becomes its own PR after v0.1, and the UI for it is already built under the *target UI ahead of functionality* decision above — nothing new is needed to hold a place for it.

  **Three constraints this puts on PR8**, all of which it now satisfies:

  1. **A keyless Provider must stay possible.** §40 lists local transcription, and Devon asked explicitly that nothing here foreclose it. `resolveProvider` previously returned `null` whenever no API key was stored, which would make an on-device Provider unreachable, so the registry now carries `requiresApiKey` and only a Provider that wants a key is gated on one. **CONTEXT.md's definition of Provider was the other blocker** and has been amended: it read *"an external service"*, which an on-device model is not. Deliberately **not** added: a `ProviderLocation = "remote" | "local"` enum. Nothing branches on it yet — `requiresApiKey` is what the code actually asks — and §37's own rule says the boundary gets created when real code needs it. Add it when a local Provider lands and something has to tell the two apart.
  2. **A Provider with no remote job must stay possible.** Already true, and Deepgram exercises it: `resume?` is optional and `transcribe.ts`'s `finish` handles its absence. The map's "`resume?`-optional interface" is the thing PR8 was built to test, and it held.
  3. **The raw Transcript is never overwritten.** Already guaranteed — §10 makes Transcripts additive and §22 makes retranscription additive — but it now has a second reason: an enriched version is a *derived* artefact, so the user can always see what the recogniser actually returned. Stage two must store alongside, never in place. That is PR9's and the enrichment PR's problem, not PR8's, but it is recorded here so neither re-decides it.

  **Also settled in passing:** speaker turns originate from the recogniser's diarization where it offers it, not from the LLM. `ProviderCapabilities.supportsDiarization` already exists and both chosen Providers set it true; PR8 does not request diarization, since §6 makes speaker identification a non-goal for v0.1 and §10's flat `Transcript.text` has nowhere to put it. The rule matters for stage two: an LLM may clean or format turns it was given, but must not be the authority for deciding who spoke, or it will confidently invent boundaries. **Note the live consequence:** storing only flat text means diarization data is discarded today, so the enrichment PR will want §10 revisited before it can show speaker bubbles.

  **And a correction worth keeping:** Anthropic ships no speech-to-text endpoint at all, so "Claude as a transcription provider" is not buildable — Claude is a stage-two candidate only. OpenAI does transcribe, which is what `custom-openai.ts` targets, but ticket 01's 25 MB cap puts it at roughly 35 minutes of audio at the measured ~96 kbps, under the one-hour reliability target — so it stays the escape hatch rather than a headline Provider. A consumer ChatGPT or Claude subscription grants no API usage either way; both bill API access separately.

- [Does two hours of audio fit through the provider?](issues/01-two-hours-through-the-provider.md): **No — not at the quality §12 demands, so chunking is in v0.1 unless Deepgram ships first.** `expo-audio`'s `HIGH_QUALITY` preset is 128 kbps AAC, making two hours **115.2 MB** against a hard **25 MB** cap at both Groq and OpenAI (5 chunks); Deepgram's cap is 2 GB (17.8x headroom). No provider offers resumable or chunked upload, and every documented workaround — Groq's `url` param and Batch API, Deepgram's callback — requires publicly-reachable audio, which §3.1 forbids. Fitting two hours into 25 MB needs 27.8 kbps, below AMR-NB. This turns chunking into a **consequence of provider choice**, not an encoding problem, and confirms §10's `Transcript` is wrong as specified if chunking lands. **Corrected by measurement at PR3 (2026-10-04):** the 115.2 MB figure above was derived from the preset's requested `bitRate: 128000`. On the project's test device (Redmi Note 10 Pro, Android 13) Android's encoder negotiates **~96 kbps** instead, measured by `ffprobe` on two real recordings — so two hours is **~86 MB**, or ~90 MB including container overhead. The decision is unchanged, since that is still ~3.5x the 25 MB cap, but the stated number is wrong and the real bitrate is the encoder's choice rather than the preset's. Also surfaced: Groq's **ASH 7.2K** rate limit is exactly two hours of audio per hour, so a single long recording exhausts the hourly allowance and §21's "failed transcription should be retryable" is unsatisfiable for up to an hour — a throughput ceiling chunking cannot relieve.

- [Can expo-audio record with the screen locked?](issues/02-record-with-the-screen-locked.md): **Yes — GO, §8's stack survives and PR3 can proceed on `expo-audio` unchanged.** First-party Android background *recording* shipped in `expo-audio@55.0.0` (published 2026-01-21); it declares its own `microphone`-typed foreground service, so no custom native module, no third-party plugin, no manual manifest edits. Config is `["expo-audio", { "enableBackgroundRecording": true, "microphonePermission": "..." }]` plus runtime `setAudioModeAsync({ allowsBackgroundRecording: true })` and a notification-permission request; a development build is required, consistent with §7. No fallback exists or is needed — `expo-av` never supported background recording and its npm `latest` is `16.0.8` from Dec 2025. **Three findings that change the plan:** (1) §38's sequencing is wrong — the *plugin* flag mutates the manifest so it must be set at **PR3**, while the *runtime* flag can wait for PR5; flipping the plugin flag at PR5 forces a native rebuild mid-roadmap. (2) **The default behaviour is the §13 bug** — `enableBackgroundRecording` defaults to `false` and `AudioModule.kt` then calls `pauseRecording()` on every active recorder when the activity backgrounds, so a foreground-only PR3 smoke test passes while §13 is silently broken. (3) **§13 + §14 cannot mean auto-resume** — Android forbids *starting* a `microphone` foreground service from the background, so PR5's "state restoration" can only mean recover-and-finalise a partial file. Also settled without needing a ticket: `AudioRecordingService.kt` hardcodes `VISIBILITY_SECRET` ("Hide from lock screen on secure devices"), so §13's "persistent system indication" is absent from the lock screen and unfixable without forking — but Android itself shows a status-bar icon whenever an app accesses the microphone on **Android 12+**, so §13's "never disguise active recording" is satisfied by the platform and this is a UX preference, not a contradiction. Residual: pre-Android-12 devices get no OS indicator. All claims verified against the published `expo-audio@57.0.5` tarball, the `AudioModule.kt`/`AudioRecordingService.kt` source, the npm registry and Android's own behaviour-changes documentation, not just Expo docs.

- **The v1.0 target UI is built in v0.1, ahead of the functionality behind it** (2026-10-05, Devon's call): `docs/UnPocketed-Example-*.png` are the target designs, and several surfaces in them — AI/exec summaries, speaker-labelled transcripts, a local Ollama provider, and "Connect Pocket Device" sync — are explicit §6 non-goals *for v0.1*. They are not non-goals for v1.0. The decision is to build the interface and scaffolding for them now, including controls that lead to placeholder or "coming soon" destinations, and wire the behaviour up later. Rationale: UI is cheap to build once and expensive to redesign incrementally, so building the whole shape now avoids reworking it at every feature. **This does not relax §6** — the *functionality* stays out of v0.1; only the interface lands early. Anyone reading §6 and finding a non-goal's UI in the tree should treat it as intended rather than as scope creep, and should not delete it.

- [How is audio written during capture?](issues/05-how-is-audio-written-during-capture.md): **One growing `.m4a`. A recording killed mid-capture is preserved but not playable, and that is the promise §14 makes.** Resolved 2026-10-07 against the [research](research/05-capture-write-strategy.md).

  **Segments are foreclosed, not rejected.** `expo-audio` does not expose `setNextOutputFile`, so gapless rotation is impossible and stop/start is the only route — and each `stopRecording()` empties `activeRecorders`, which tears the foreground service down (`AudioRecordingService.kt:160-169`), so every subsequent segment re-runs `startForeground(…, FOREGROUND_SERVICE_TYPE_MICROPHONE)` **from the background**. That is the operation [ticket 02](issues/02-record-with-the-screen-locked.md) established Android forbids. Segmented capture is therefore off the table on a platform constraint, which also makes the ticket's question 2 moot.

  **The crux:** `MPEG4Writer` writes the `moov` atom only at stop, so a killed process leaves `ftyp` plus an unterminated `mdat` — every byte of audio, no index. There is **no on-device repair path**; `MediaExtractor` needs a parseable `moov`, and off-device `untrunc` wants a reference file from the same encoder. `3gp` uses the same writer, so it is not an escape. `aac_adts` **was** an escape — self-describing per frame, same AAC-LC bitstream, accepted by both chosen providers — and was **considered and declined** (Devon's call) because ADTS carries no sample index, so §16's seek and duration would become bitrate estimates and PR4 has already shipped tap-to-seek and ±15s against exact ones. Revisit only if partial recordings turn out to be common in practice.

  **So §14's "survive unexpected application termination" means the bytes survive, not that the file plays.** Recovery, decided with it: an orphan is **adopted into the library automatically** on launch rather than offered behind a prompt, because §3.2 should not make preservation conditional on the user noticing a dialog; it is **flagged as interrupted and not playable** per §32; it is **exportable as the raw file**, since off-device repair is the only remaining route to the audio and §3.4 makes that the user's right; and its **duration is estimated from file size** against the measured ~96 kbps and labelled approximate, because 0:00 reads as a bug and the user's real question is how much they still have. Note the estimate's divisor is device-specific — the encoder negotiates it — so it is approximate for that reason as well as from the missing index.

  **PR5's "state restoration" is now defined, and it is narrower than §38 implies.** It cannot mean recover-and-*finalise*: a `moov` cannot be synthesised on-device. It means **recover-and-adopt**. Conveniently, the capture directory and the library directory differ, so everything in `Paths.document/Audio/` is an orphan by definition, and a playable one — finished but never filed — is distinguished from a killed one by whether the player loads it, which PR4's duration backfill already does.

  **Question 4, who owns a stop JS never saw:** the notification's Stop button reaches native `stopRecording()` directly, finalises the file **correctly**, and emits `recordingStatusUpdate`. Before PR5, the app passed no listener to `useAudioRecorder(options, statusListener?)`, so it missed the event and remained in `"recording"`. PR5 added the listener and the runtime `allowsBackgroundRecording` flag; the notification's stop can now file the recording without a screen press.

  **Fixed in code when found, not deferred:** capture was writing to the **cache** directory (`AudioRecorder.kt:241` resolves `options.directory ?: RecordingDirectory.CACHE`, and the `HIGH_QUALITY` preset sets none), so an hour-long recording grew where Android may evict it. Now `directory: "document"`. This decision makes that load-bearing rather than tidy: if the bytes are all that survives, losing them to eviction loses the recording outright.

  **Spec consequences:** §16's "Every recording must be playable" now has an exception and should say so — a recovered partial is a Recording that cannot be played. §14 should state what "survive" buys, so nobody re-derives it. §38's PR5 wording "state restoration" should read recover-and-adopt.

  **Deferred hardening from the v0.0.4 review (2026-10-07):** (1) If an interrupted file is moved into the library but its sidecar write fails, `recoveredSidecar` currently marks it complete; probe the MP4 index when rebuilding metadata without a sidecar. (2) `containsMoov` currently accepts a `moov` header without checking that the declared box fits in the file; a process killed while writing that box can therefore be marked playable. Source TODOs mark both sites. Devon chose to revisit these later.

- **The reliability target is one hour, not two** (2026-10-07, Devon's call — and the spec already agreed). "Two hours" appears in the spec only in §34's and §36's **testing** lists; the sole place a trust threshold is stated is §38's PR5 exit condition, *"An hour-long real-world recording can be trusted."* Tickets 01 and 04 both treated the test figure as a requirement, which inflated their analysis. One hour at the measured ~96 kbps is **~43–45 MB**, not ~90 MB: still far over Groq's and OpenAI's 25 MB cap, so nothing reopens there, but it halves the uplink needed to clear Deepgram's ambiguous 10-minute `504` (~600 kbps rather than ~1.2 Mbps). [Ticket 04](issues/04-which-provider-ships-first.md) stands — its decisive argument was Deepgram storing no transcripts, which duration does not touch. Multi-hour recording as a **paid** tier was raised and is **not** recorded as a decision: §3.5 forbids "artificial limitations that can later be removed by a subscription" by name and §6 lists subscriptions as a non-goal, so it would need §3.5 amended first. A *technical* ceiling in v0.1 needs no amendment and is what §38 already says.

- [Which provider ships first?](issues/04-which-provider-ships-first.md): **AssemblyAI at PR7, Deepgram plus `custom-openai.ts` at PR8, and chunking is out of v0.1 entirely.** Adopted 2026-10-07 against the [research](research/04-provider-selection.md), which **contradicted this ticket's own pre-argued "Deepgram first" position**. Two findings moved it. (1) **The candidate pool was drawn too small.** AssemblyAI clears a two-hour file at **2.2 GB** by direct byte upload and documents that the resulting URL is *"only accessible by our API"* — so §3.1 is satisfied rather than merely tolerated, unlike Groq's `url` (needs *us* to publish audio) or Deepgram's `callback` (needs *us* to host an endpoint). There were **two** chunk-free providers, not one, which freed the first-provider choice from the upload cap altogether. (2) **Deepgram cannot implement §21.** Its docs: *"Deepgram does not store transcripts, so the API response is the only opportunity to retrieve the transcript"*, and §3.1 removes the callback that would decouple retrieval. A two-hour upload whose HTTP response is lost — app killed, network change, Doze — therefore loses the transcript **permanently, with no server-side state to query on relaunch**; `Transcribing` becomes a local fiction and recovery costs a ~90 MB re-upload and a second bill. AssemblyAI's `queued/processing/completed/error` maps onto §21's four states and a persisted job id makes `Transcribing` survive app death. Ordering follows from **interface asymmetry**: an interface built for async jobs absorbs a synchronous provider for free, while the reverse needs a breaking change at PR8 *after* transcripts exist in SQLite. AssemblyAI is also cheaper — **$0.15/hr** (universal-2) against ~$0.258/hr — and does not bill failed jobs, which is precisely §21's retry path. **Accepted costs:** AssemblyAI retains data where Deepgram retains none — audio deletion *"begins at 24 hours and is at most 48"*, transcripts 30 days with TTL presets down to 1 day — and **zero data retention covers the streaming product, not the async endpoint we would use**, so a privacy-maximising user cannot configure their own account to store nothing. Also a heavier PR7 (upload, submit, poll, persist a job ref, resume) and $50 of free credit against Deepgram's $200. **Quality is explicitly unverified** — the decision rests on caps, limits, lifecycle, price and §3.1 compliance, all documented, and §22's retranscription plus PR8's switch make it low-regret. **Consequences:** §19's `Groq`/`whisper-large-v3-turbo` mockup is now actively misleading and should read `AssemblyAI`/`universal-2`; §19 needs a retention sentence naming both windows and must not imply async zero-retention is available; §18 needs a `ProviderCapabilities` surface and a job-ref callback, but **no** progress or partial-result surface, since that was premised on chunking; §10's `Transcript.text` **survives unchanged**, so the no-ORM decision's revisit trigger does not fire. Groq's 25-vs-100 MB documentation conflict is left **unresolved and moot** — its ASH 7.2K ceiling rules it out of first place independently of file size. Not examined: ElevenLabs Scribe, Speechmatics, Gladia — the pool closed at the first provider meeting every constraint, and the research says so rather than implying a survey. **Corrected at PR7 (2026-10-08):** the pre-recorded endpoint takes `speech_models` (plural array), not the singular `speech_model`, which is now streaming-only; a newer `universal-3-5-pro` exists and is the default alongside `universal-2`, so PR7 pins `["universal-2"]` explicitly to hold the costed price; and the completed transcript reports `speech_model_used`, which is what §20's model attribution is taken from. The provider choice, price and lifecycle are unaffected.

- **Stay on Expo SDK 57 for v0.1; no scheduled re-evaluation** (2026-10-07, Devon's call): the SDK moves only if something **blocks** us on 57, or a **serious security flaw** makes staying untenable. This **supersedes the scheduling clause** of [Which Expo SDK ships v0.1?](issues/00-which-expo-sdk-ships-v0-1.md) — "SDK bumps are accepted but scheduled, re-evaluated once at PR3" — and the "revisit at PR10" note that went with it. The re-evaluation it asked for has happened and its answer is now a standing rule rather than a recurring question. Rationale: PR3 **already paid** for 57's two named `expo-audio` bugs — the notification-before-prepare sequencing in `src/features/recording/permissions.ts` and the JS-side timeout in `src/lib/with-timeout.ts` — so the cost of staying is sunk, while a bump re-opens the entire dependency graph for an app whose whole promise is that recordings are never lost. **Consequence:** those two workarounds are load-bearing for the foreseeable life of v0.1, not temporary scaffolding, and must not be removed as redundant. A bump, if one is ever forced, is its own piece of work with its own device verification, not a step inside another PR.

- **Raw `expo-sqlite`, no ORM** (2026-10-07, taken at PR4 against §8's own rule): §8 permits an ORM "only if it materially improves migrations, type safety, or maintainability", and this map parked the call until real migrations existed. They exist now, and the rule points at raw SQL. v0.1's schema is one `recordings` table, plus `transcripts` at PR7; migrations are forward-only and driven by a `PRAGMA user_version` check, which is about twenty lines. Drizzle would add a codegen step, a `drizzle-kit` dev dependency and a second source of schema truth to replace those twenty lines, and it would not buy the type safety either — rows are mapped to `Recording` from `src/types` through a single function, which is the one place a column rename can bite. **Revisit if** chunk assembly lands (see the first *Not yet specified* entry): joins and partial-row updates are where an ORM starts earning its keep. Note also that SQLite here is an *index*, not the source of truth, which lowers the cost of being wrong — the schema can be dropped and rebuilt from disk.

- **Home and Library do not merge** (2026-10-07, Devon's call, taken at the start of PR4's persistence work): §29 left this open — merge them "if they naturally become the same screen" — and called it an observation rather than a decision to take in advance. The Home screen added in v0.0.2 made it observable for the first time; until then both screens read the same mock list, so there was nothing to observe. They stay separate because they differ in **job**, not in content: **Home is a launcher** — hero actions, tiles, and the two most recent recordings as a shortcut — while **Recordings is the library**, and §15's affordances (chronological display, rename, playback, deletion, transcript status) live there alone. Home links to it rather than duplicating it. Recorded here so PR4 resolves the question deliberately rather than by implementation, which is the trap the PR4 scope note names.

- **Styling moves from NativeWind to Uniwind** (2026-10-04, Devon's call, taken at the start of PR4 before UI work): **Uniwind 1.12.1 + Tailwind 4.3.3**, replacing NativeWind 4.2.7 + Tailwind 3.4.19. The decisive argument is availability, not speed: **NativeWind has no stable Tailwind 4 line** — `nativewind@latest` is 4.2.7 against Tailwind 3, and the Tailwind 4 branch is `5.0.0-rc.0`, still an RC. This is the same released-over-prerelease test that kept the project on Expo SDK 57, pointing the other way. Uniwind is 14 months old, 73 releases, stable since 1.0, and compatible with our react 19.2.3, react-native 0.86.3 and Expo SDK 57. Performance is a real secondary gain and the **free tier carries it** — the vendor benchmark puts Uniwind free at 60.7 ms against NativeWind 4's 138.1 ms (~2.3x); **Uniwind Pro is commercial** and its C++/ShadowTree engine, `className` Reanimated and native theme transitions are all paywalled, but nothing Unpocketed does needs them. Config shrank: **no Babel plugin and no `tailwind.config.js`**, with `tailwind.config.js` and `nativewind-env.d.ts` deleted outright and tokens moved into Tailwind 4's `@theme` in `src/global.css` at identical values. Two predictions in the migration plan proved wrong and are worth recording: `@tailwindcss/oxide` and `lightningcss` ship prebuilt per-platform binaries and need **no** `allowBuilds:` entry, and `expo/types` already declares `*.css`, so NativeWind's module declaration was redundant. `nodeLinker: hoisted` was deliberately left in place and remains **untested** without NativeWind. **Known regression:** browser-based development is broken by the switch — the web bundle serves but React never mounts, via an upstream circular import when `react-native-web` 0.21.3+ loads the RN root through `InputAccessoryView` ([uni-stack/uniwind#704](https://github.com/uni-stack/uniwind/issues/704), open; fixed and regressed three times). We run exactly 0.21.3. Android is unaffected, and §6 makes a web surface a non-goal, so this costs a development convenience rather than a product capability — but it is a real cost that NativeWind did not have. Open consequence: `docs/spec.md` §38's PR1 deliverable list still names NativeWind as a record of what that PR shipped.

- [Which Expo SDK ships v0.1?](issues/00-which-expo-sdk-ships-v0-1.md): **SDK 57, with both workarounds; SDK bumps are accepted but scheduled, re-evaluated once at PR3.** `expo` `latest` was `57.0.26` against a three-day-old `next` of `58.0.3`. The risk is asymmetric — 57 carries two named, bounded, fixable bugs, while 58 puts the entire dependency graph against a days-old pre-release, and for an app promising recordings are never lost, known bugs beat unknown ones. Also: one of the two "workarounds" isn't one — §13 forces a `POST_NOTIFICATIONS` request anyway, so requesting it before `prepareToRecordAsync` is just correct sequencing. **Two things now belong to PR3, not PR5:** request the notification permission before preparing (with a §32 error path for refusal), and wrap `prepareToRecordAsync` in a JS-side timeout, since the library's own never fires. PR1 is unblocked.
