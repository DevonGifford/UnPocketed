# What is an edited transcript?

Type: grilling
Status: resolved
Map: [De-risk v0.1](../map.md)

## Resolution

**An edit produces a new Transcript whose `source` records who wrote it, and editing happens per speaker turn.** Resolved 2026-10-08 by grilling, before PR9 started.

Two facts reshaped the question before it was answered. §38's PR9 deliverables **already list "multiple transcript versions"**, so the spec anticipated more than one record per transcription and the new-record option costs less than this ticket assumed. And the ticket's own closing caveat — *"expect to state the answer in a way that survives `Transcript` later gaining a segment concept"* — **came true the day before it was taken**: PR8 added diarization, so a Transcript now carries speaker-attributed `segments` as well as flat `text`, and editing one invalidates the other.

### What was decided

1. **An edit produces a new Transcript**, linked to its parent, rather than mutating one or setting a flag. Editing an *already-edited* transcript updates that same record instead of chaining — once a human owns the text there is no model provenance left to protect, so one edited descendant per original is enough. The flag option was rejected because it makes `text` mean two things and leaves §20 answerable only with a caveat; the patch-layer option was rejected as too much machinery for v0.1 (§3.6); deferral was rejected because §5 item 13, §23 and §38's PR9 all require editing.

2. **`source` records the *author*, not a boolean.** This came out of the enrichment decision below: an LLM cleaning up a transcript is the same operation as a human editing one, performed by someone else. A single author field covers both and keeps §20 answerable at every step, instead of building a second mechanism for the same thing.

3. **Editing is per speaker turn**, with flat `text` regenerated by joining turns. The alternatives both fail: dropping segments on edit costs the user the whole speaker view for one typo, and keeping them costs the truth — the turns would describe text that no longer exists. A non-diarized transcript is the single-turn case, so one editor serves both. Crucially this never re-derives speaker boundaries from edited text, which would be guessing who spoke.

4. **Export states origin and edit separately.** `Provider:` and `Model:` stay — they are true as a statement of origin — and an `Edited:` timestamp plus the parent id stops them being read as a claim about the current text. JSON carries the same structurally, so an export round-trips.

5. **Deleting a parent and deleting its edit are independent.** Cascading would destroy the user's own writing in order to remove a machine's output, inverting §3.2's instinct; refusing would leave a record they cannot remove. The edit keeps its parent's `providerId`/`modelId`, so its origin survives — it simply can no longer be diffed, which is a loss the user chose.

6. **Speaker labels are not editable in v0.1.** Naming a speaker is a claim about who a person is, and it immediately raises the same voice appearing in another recording under a different index — speaker *identification*, a §6 non-goal with real privacy weight (§26). Editing a turn's words is ownership of your own transcript; naming a voice is a different feature wearing the same jacket.

7. **An edit becomes a record on an explicit save**, with a warning when leaving with unsaved changes. A derived Transcript is something the user chose to make; a half-typed word is not. Persisting the buffer as a promotable draft would be safer and is deliberately not built: it is a second storage concept for one screen, and worth a ticket only if editing turns out to happen in long sessions.

### Scope change taken with it

**Transcript enrichment is in v0.1** (Devon's call, overriding §6's "automatic summaries" non-goal). The recommendation was against — and the argument that lost is worth recording, because it is the same test that decided diarization the day before, pointing the other way. Diarization had to ship in PR8 because **speaker data is unrecoverable later**: it exists only if the recogniser is asked for it at transcription time, so fixing it afterwards means paying to upload and transcribe the audio again. A Brief is **regenerable** from text already on disk, for an LLM call and no re-upload, so nothing is lost by waiting. Devon decided the user-facing value justified it regardless.

Consequences, all settled in the same session:

- **Enrichment is its own PR, after PR9 and before PR10.** Folding it into PR9 — already editing, versions, three export formats and audio sharing — would make it unreviewable. Export is written driven by whichever fields a transcript has, rather than a fixed template, so enrichment fields are additive rather than a rewrite.
- **Enrichment produces two artifacts, not one.** Cleanup produces a derived **Transcript** (see 2 above). The title, sub-headline, executive summary, overview and conclusion become a separate entity, the **Brief**, owned by a Transcript and carrying its own `providerId`/`modelId`. Fields are all optional: if a model returns no conclusion, the Brief has none and the interface shows nothing rather than a heading over filler (§3.7). Many Briefs per Transcript, so two LLMs can be compared — §22 one layer up.
- **Two provider registries, sharing credential storage and UI.** One registry would put a speech recogniser and a summarising LLM in the same picker, which is the blur this whole split exists to prevent. Key storage is already scoped by provider id and does not care what kind of provider it is. **Which** LLM providers ship first is a separate research question, as ticket 04 was for transcription.
- **Enrichment runs on demand, never automatically.** Same regenerable/unrecoverable test: running it unasked spends the user's money on something they can always get later.
- **A Brief is not editable in v0.1.** The escape hatch for a bad one is to regenerate it, possibly with another model — §22's pattern again rather than a new mechanism, and far cheaper than duplicating the author-provenance model for a second entity.

### Spec consequences

§6 must drop "automatic summaries" as a non-goal; §5 gains success criteria for enrichment; §10's `Transcript` gains `source`, a parent link and the segment concept PR8 added; §20's question needs to stay answerable for an edited transcript; §24's Markdown example needs the edit provenance lines; §38 gains the enrichment PR. CONTEXT.md gains **Brief** and the author-provenance vocabulary.

Everything below is the question **as originally posed**, kept for the record.

## Question

The spec contradicts itself. Three statements cannot all hold:

- **§23** — the transcript screen supports **editing**.
- **§20** — "A transcript should always make it possible to answer: *Which provider and model generated this?*"
- **§10** — `Transcript` has a mutable `text` field, an `updatedAt`, a `providerId` and a `modelId`, and no flag distinguishing model output from human-edited text.

Once a user fixes three misheard words, the record still claims `modelId: whisper-large-v3` but the text is no longer what that model produced. §22's whole point — that provider choice becomes "verifiable rather than ideological" because users can compare transcripts themselves — quietly breaks: you can no longer tell whether you are comparing two models or one model and one careful proofread.

What should the model be? Candidates to grill, not a menu to pick from blind:

- An edit produces a **new** `Transcript` with a distinct source (`human-edited`, deriving from its parent) — provenance stays honest, at the cost of more records and a parent/child relation.
- The existing record gains an **edited flag** plus the original text retained alongside — cheaper, keeps one row per transcription, but now `text` has two meanings.
- Edits are a **separate layer** over an immutable transcript (a diff or patch set) — strongest provenance, most machinery, probably too much for v0.1.
- Editing is **deferred out of v0.1** entirely — but §5 item 13 lists "edit or copy transcript text" as an MVP success criterion, so this needs an explicit decision, not a silent drop.

Also settle the downstream consequences, since they are what make this worth deciding now rather than at PR9:

- What do §24's Markdown and JSON exports state about provenance for an edited transcript? The §24 example prints `Provider:` and `Model:` with no room for "edited by hand."
- Does §25's deletion model change — can the original model output be deleted while keeping the edit, or vice versa?

## Note on ordering

Previously blocked on the chunking question, now unblocked. Chunk assembly is about how `text` is *produced*; edit provenance is about what happens *after* it exists. They touch the same entity but are separable, so this is a cheap HITL ticket takeable alongside the heavier ones — just expect to state the answer in a way that survives `Transcript` later gaining a segment concept, should [Which provider ships first?](04-which-provider-ships-first.md) land on a 25 MB provider.
